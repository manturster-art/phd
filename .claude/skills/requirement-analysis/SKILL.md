# Requirement Analysis Skill

PM 에이전트가 사용. 대학원 원우회 앱의 요구사항을 구조화된 명세로 만든다.

## 워크플로우

### 1. 사용자 의도 파악
초기 요청에서 명시된 것과 빠진 것을 분리한다. 다음 항목을 반드시 확인:
- **가입 방식**: 이메일+학번 승인? 초대 코드? 학교 SSO?
- **회원 단위**: 학과 전체? 특정 연구실/기수?
- **공개 범위**: 비로그인 열람 가능? 회원만?
- **임원 구조**: 회장/총무/학번 대표 등 역할
- **회비/행사 처리 수준**: 정산 시스템? 단순 공지?

명시 안 된 항목은 합리적 기본값으로 가정하고 "ASSUMPTION" 라벨로 명시. 사용자가 곧 정정할 수 있게 함.

### 2. 페르소나 도출
원우회 맥락에서 자주 등장하는 페르소나:
- **신입 원우**: 정보 탐색 위주, 가입 직후 행사·선배 정보 갈증
- **임원/총무**: 공지 작성, 회비 관리, 행사 운영
- **고학년/졸업 예정자**: 가벼운 참여, 모임 알림 위주
- **졸업생(선택)**: 동문 네트워킹 — MVP에선 보통 제외

각 페르소나의 1~2주차/1학기/졸업까지 사용 패턴을 짧게 기술.

### 3. 사용자 스토리 작성
"As a [역할], I want [기능], so that [가치]" 형식. 다음 도메인 그룹으로 묶는다:
- 인증/계정 (가입, 로그인, 프로필)
- 공지 (작성, 조회, 알림, 핀)
- 게시판 (글 작성, 댓글, 좋아요, 검색)
- 일정 (등록, RSVP, 캘린더 뷰)
- 회비/행사 (납부 확인, 참가 신청)
- 회원 (디렉토리, 권한 관리)
- 관리 (신고 처리, 게시글 숨김)

각 스토리에 P0/P1/P2 라벨. P0는 MVP에 반드시 있어야 동작하는 것만.

### 4. 권한 매트릭스
역할 × 액션 표를 만든다:

| 액션 | 비회원 | 일반회원 | 임원 | 관리자 |
|------|--------|---------|------|--------|
| 공지 열람 | △ | ○ | ○ | ○ |
| 공지 작성 | × | × | ○ | ○ |
| 게시글 작성 | × | ○ | ○ | ○ |
| 자기 게시글 삭제 | × | ○ | ○ | ○ |
| 타인 게시글 숨김 | × | × | ○ | ○ |

(△ = 일부 공개, ○ = 가능, × = 불가)

### 5. 비기능 요건
원우회 앱에서 기본으로 명시할 것:
- 모바일 우선 (스마트폰 비율 90%+)
- PWA (앱스토어 심사 회피)
- 한국어 우선, 시간대 KST
- 접근성: WCAG AA 수준 목표
- 개인정보: 학번/연락처 노출 범위 명시

## 출력 형식

`_workspace/01_pm_requirements.md`에 위 5개 섹션 + "열린 질문" + "변경 로그"를 마크다운으로 작성.

## 재실행 시
이전 파일이 있으면 읽고, 사용자 피드백을 반영해 해당 섹션만 수정. 변경 로그에 날짜와 변경 사유 추가.
